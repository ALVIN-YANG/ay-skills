# 技术文章：从材料到读者能用的答案

适用于技术原理、选型、实操和索引文章。下面是可往返的写作流程，不是固定目录；信息已经明确就直接写，局部改稿只做相关检查，不额外要求提纲审批或过程文件。

## 1. 确定读者要获得什么

把目标写具体。例如“能根据任务依赖关系选择多智能体架构，并知道如何验证”，比“全面介绍多智能体”更能决定取舍。确认必要的读者前置知识，不把术语、知识点数量或文章长度当作完成目标。

原理文章服务于理解，选型文章服务于决定，实操文章服务于完成任务，索引服务于查找。可以在一篇文章中组合，但要有主要阅读目标，不强制所有文章都包含方案对比、代码、踩坑和评测。

## 2. 先确认材料覆盖，再提炼观点

用户指定原文时，先读取与请求范围相关的正文、图表及限定条件。对照用户要求，确认要解释的概念、方案和结论是否都有依据。搜索摘要或部分摘录不等于完整原文；无法获取时说明可见范围，不用一篇泛泛介绍冒充原文解读。

如果已有可靠的一手材料能够回答同一问题，可以据此继续，但要说明依据，不能声称读过未获取的内容。缺口会改变核心结论时，先指出缺少什么以及影响；不要自行更换问题来掩盖缺口。

区分来源中的事实、实验观察、作者解释和自己的工程建议。记录会影响结论的版本、基线、分母和约束，避免混用不同版本的数据。“同组方案里最好”不等于优于基线；试验观察不能直接变成普遍保证。正文只保留理解结论所需的来源信息，不叙述工具检索过程。

## 3. 先形成核心回答，再安排阅读顺序

有足够依据后，先形成带条件的核心回答；后续证据推翻它时，连同开头一起改。开篇写答案和重要限制，不用“本文将介绍”替代答案，也不要为了先给结论而编造唯一推荐。

随后按读者的疑问推进：要解决什么、关键机制是什么、为什么会得到这个结果、在什么条件下结论改变。只选当前文体需要回答的问题，不把这个顺序变成每篇文章的通用目录。每节应增加新的解释、证据或边界，而不是重复开头。

原文目录、搜索顺序和代码目录都不天然等于读者的理解顺序。比较方案时先选共同的问题和比较依据，避免每个方案使用不同场景，最后无法作出选择。

## 4. 用具体过程补齐理解所需的中间步骤

围绕材料支持的场景说明输入、参与者、动作、结果和原因；假设的场景要标明。技术选型尤其需要走到“这些约束下为什么排除它、为什么保留另一个”，不能用产品案例证明某方案存在以后就停下。

先用隐私、资源位置、兼容性或法规等硬条件排除不可用方案，再比较成本、可靠性、安全性和维护负担。把部署位置、隔离方式、供应商等不同问题分开，不混成重叠的类型。材料不足以选出唯一方案时，说明哪项条件会改变选择。

首次使用关键术语时补上读者需要的解释。普通动作能讲清时，不引入额外黑话；确实有区分作用的术语则保留。用反例或条件变化说明边界，不靠堆更多同类例子显得全面。关系难以用文字比较时再配图，不用装饰图代替解释。

## 5. 按文章目的验收

| 文章目的 | 只看成文，读者应能做到什么 |
| --- | --- |
| 原理解释 | 说清关键术语、因果关系和边界；能解释一个条件改变后为什么结果会变化。不要求必须照着部署。 |
| 技术选型 | 从约束走到排除项、剩余方案和建议，知道代价及改选条件；不止记住一张优缺点表。 |
| 实操或案例复盘 | 知道前提、步骤、预期结果、失败后的处理以及验证方式。示例代码、假设演练和已实测结果不能混写。 |
| 技术索引 | 能按问题或分类定位术语与方案，看懂相邻概念的区别，找到可信的深入资料；标明易过时信息的适用版本。 |
| 指定材料解读 | 覆盖用户要求的观点与方案，保留原文的限制；读者能分辨原文说了什么、文章补充了什么。 |

## 6. 分开检查正确性与可读性

先核对事实、例子、数据和建议是否相互支持；可执行示例按风险验证，不能为测试方便换掉原来的验收目标。

再只看正文和读者背景，检查能否回答最初的问题，不借研究笔记补全缺失前提。删去重复结论和不服务于主问题的内容，修复指代不明、概念跳跃与未解释的术语。选型建议不在开头、对照表和结尾反复完整复述；后面只补新的理由或例外。

AI 审稿和读回检查只能发现部分障碍，不证明真人已经理解。有真实读者反馈时，优先记录他在哪一段需要回读、误解了哪个条件，并据此修订；不要只凭流畅度评分宣称完成阅读验收。
