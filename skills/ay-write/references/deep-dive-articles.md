# 技术深度拆解：行文与手写 SVG 机制图

系统、框架、协议、记忆项目的完整拆解文章（存储、写入、召回、冲突、成本逐层展开）使用本文件的行文和配图风格。基准样例是 alvin-notes 的 `src/content/docs/claw/openclaw/9-memory-system-deep-dive.md` 及其 `public/images/claw/openclaw/memory-system/*.svg`；新文章成稿后对照样例检查风格是否一致。题库、教程、参考条目、社媒内容不继承本文件。

## 开篇：先给判断，再给例子

首句给出全文最重要的工程判断，说清这个系统真正难在哪里、什么决定它有没有用。判断必须来自材料支持的真实取舍（例如“检索只是找回手段，写入规则和来源检查才决定记忆有没有用”），不凭空制造“不是 A 而是 B”的对立。

两段之内给出核心结论，紧跟一个具体、日常、能贯穿全文的例子，用 `text` 代码块列出时间线：

```text
周一，你说：“我喜欢蓝莓，芒果吃了不舒服。”
周二，你让 Agent 买水果，它最后买了蓝莓。
周五，你问：“之前买了什么？为什么没买芒果？”
```

优先用吃水果、买东西这类日常场景，不用低频、抽象的企业场景。例子中难以对应到系统的角色或动作，在讲到对应机制时解释。概览图放在开篇例子之后，再注明固定版本与来源范围。

## 结构：编号章节回答实际问题

按读者的理解顺序组织编号章节，每个标题是一个具体问题：“先分清哪几个概念”“数据写到哪里”“什么时候触发写入”“新会话怎样找到旧内容”“冲突和遗忘怎么处理”“安全与成本容易误判在哪里”“怎样排查”。典型顺序是概念区分 → 存储位置 → 写入 → 召回 → 检索细节 → 冲突与删除 → 安全与成本 → 更换与排查；按主题增删，不机械套目录。

存储、写入、召回是三条独立主线，分别讲清：触发条件是什么、谁来判断、具体逻辑、失败时发生什么。不要把它们揉成一条“工作流程”。

## 每节的写法

- 先给本节的结论，再展开机制。
- 术语首次出现用一句白话解释：“SQLite 是运行在本地文件里的数据库”“token 是模型计算文本长度的单位”。英文名词保留原文并配中文说明，不堆砌不解释的英文术语。
- 用开篇同一个例子走机制，每节推进例子的下一步，不另起新例子。
- 关键规则引用真实代码常量、配置或默认值，并链接到固定版本的源码文件；公式必须配具体数值演算或小表，让读者能自己算一遍。
- 真实存在的常见误解要明确纠正：“ADD-only 不等于自动解决冲突”“能被搜索不等于值得信任”。纠正完要说清正确的规则是什么。
- 重要结论加粗单独成段，一节最多一处。
- 保留门槛数值、失败分支、版本差异和来源边界；通俗不等于删掉这些深度。查不到的具体实现细节不写，不编造权重、默认值或内部表名。
- 重要模块就近配一张手写 SVG 机制图，图与正文回答同一个问题。

## 语言

简单句，不啰嗦，不堆抽象词。每段只增加新信息；同一结论不在多个标题下重复。不写“本文将介绍”，不写幕后检索过程，结尾不追加“总结”套话。代码示例未实际运行时，在代码附近明确声明。

## 收尾

读者需要查表名或配置项时，把正文未展开的查阅细节放入附录。版本与来源范围在开篇注明一次，具体规则就近给出处。

## 手写 SVG 机制图（默认配图）

深度拆解文章默认配 6–8 张手写 SVG：1 张整体概览 + 每个核心模块 1 张机制图。精确机制图不用 Mermaid、图片生成或截图替代。保存到文章所属分类的图片目录（如 `public/images/<category>/<topic>/01-overview.svg`），文件名带序号，正文配有用 alt 文本。

### 画布与字体

- `viewBox="0 0 1440 H"`，宽度固定 1440，高度按内容 750–1150；`role="img"` + `<title>` 说明图的结论。
- 整图背景 `fill="#fbfaf6"`。
- 字体 `system-ui, -apple-system, "PingFang SC", "Microsoft YaHei", sans-serif`，正文文字 `fill="#24282f"`。
- 标题 38px/700 放在 `(60, 68)`；副标题 24px `fill="#6b6f76"` 放在 `(60, 112)`，写版本、范围或一句话流程。
- 文本层级：`.head` 26–27px/600 为卡片标题；`.body` 24px 为正文；注释 24px `fill="#6b6f76"`。

### 配色（固定调色板）

| 用途 | fill | stroke |
| --- | --- | --- |
| 蓝：输入、渠道、外部来源 | `#e7edf3` | `#b9c6d4` |
| 橙：核心处理、评分 | `#f9ecdf` | `#e0b48f` |
| 紫：运行时的复杂模块 | `#efe9f4` | `#c3b4d6` |
| 绿：输出、模型与工具 | `#e4ecdf` | `#a9c0a4` |
| 米白：存储与普通卡片 | `#fffef9` | `#c9c2b2` |

强调色：箭头与关键标记 `#d97745`；图内强调文字、公式 `#b35c2e`；次要关系用 `#8a8f98` 灰色虚线（`stroke-dasharray="8 6"`）。终点/结论卡可用 `#d97745` 实底白字。

### 布局与内容

- 卡片 `rx="12"–"14"`、`stroke-width="2"`；分组容器用 `fill="none"` + 橙色虚线框。
- 步骤用 ①②③ 编号；箭头上写条件标签（“不能回答”“强命中”），箭头 `stroke-width="3"` 并配 marker。
- 图内放文章真实例子的原文、真实公式和数值结果（如 `matchScore = 0.85 × 0.8 + relevance × 0.2`），不写“步骤一”“数据”这类占位词。
- 底部放 1–3 行注释，写限制和易误判点（“没有找到不等于历史上没有”）。
- 一张图只回答本模块的问题；概览图展示模块之间的关系，局部图展开机制。

### 可校验标注（必须）

项目用浏览器校验 SVG 布局，手写时遵守：

- 每个装文字的矩形带 `id="node-N"` 和 `data-svg-box=""`；其中每行文字带 `data-svg-container="node-N"`。
- 不属于任何卡片的独立文字（标题、箭头标签、注释）带 `data-svg-label=""`。
- 文字在容器内边距 ≥16px，任意两行文字不重叠，所有元素在 viewBox 内。
- 不使用 `foreignObject`、`script`、`image`。

### 验收

项目提供校验时必须通过：alvin-notes 用 `npm run svg:check -- --update`（新图先逐张 `--file=` 检查），再运行 `npm run fonts:update` 和 `npm run build`。缩略图尺寸看主题和层次，原尺寸看标签可读性、箭头方向、条件标注和事实是否与正文一致。
