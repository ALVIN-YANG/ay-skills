# 评测协议、指标和实验记录

按当前任务选读：建立协议读第一节；分析数据与评分读第二、三节；连续迭代读第四节。字段是记录建议，适配已有项目格式，不要求全部落成新文件。

## 一、评测合同

在开始昂贵或连续运行前，将会影响接受结论的项目写清楚。沿用已确定的需求和授权，避免重新审批。

| 项目 | 应记录的内容 |
| --- | --- |
| 目标 | 用户任务，以及可观察的最终结果 |
| 对象 | 基线、候选实现与变更项；代码提交或内容指纹 |
| 配置 | 模型标识、可用的固定版本、提示词和工具版本、采样设置、实际加载的配置与技能 |
| 数据 | 数据版本、来源、分组、发现/回归/留出用途及已暴露范围 |
| 状态 | 初始会话、记忆、数据库或工具快照；如何隔离和恢复 |
| 评分 | 规则、裁判模型和量表版本；人工校准证据 |
| 接受 | 必须改善的指标、不可突破的限制、可接受的退化与不确定性 |
| 预算 | 时间、费用、调用量或实验轮数的适用上限；从何处读取实际消耗 |
| 停止 | 成功、无有效进展、执行失败、预算到限或需要用户决定时的动作 |
| 范围 | 可读写对象、环境和已授权外部动作 |

预算不应由运行耗尽后再反推。没有估计时，先在已有授权内做小规模测量，给出运行成本估计和建议上限。不能据此擅自启动昂贵的多日循环。

模型别名、外部工具或在线知识不可完全固定时，记录时间、实际返回的版本和可观察变化。不要承诺绝对复现；随机种子和低采样温度也不构成确定性保证。

## 二、数据与运行设计

### 覆盖和分组

用失败类别和用户影响选择案例。对某个行为同时覆盖“应该发生”和“不应该发生”的场景，防止一侧优化。例如，修复不调用工具时，还需检查本来无需调用工具的场景。

同一用户、同一段会话、同源改写或高度重复案例放在同一数据分组。留出集不向执行修改的 Agent 提供逐例反馈；如用于后续修复，将其转为发现数据，并使用新的独立验收证据。

诊断集可以包含更多困难案例。用其通过率推断线上整体收益时，需要说明真实流量分布和加权依据；只有 badcase 的通过率不能代表生产成功率。

### 两种对话测试

- 固定历史重放：固定此前的用户与助手消息，检查下一步回答或动作，适合定位局部行为。
- 完整任务：允许新版本改变后续对话路径，检查最终任务结果、轮次和恢复能力。使用模拟用户或模拟工具时，标记模拟部分，并保留必要的人工真实体验验收。

### 隔离与可比性

会话、记忆、文件、缓存、隐式加载的全局配置或技能及外部系统状态会影响下一次试验。核对实际加载内容，不能只凭临时工作目录声称隔离。从等价快照开始，或使用独立测试资源；共享环境中的资源竞争也可能造成相关失败。重复试验并不自动增加独立样本数。

在基线与候选间按案例配对比较。必要时交错或打乱运行顺序，以减少在线服务漂移和时段效应。并发度根据隔离能力和限流确定；真实外部副作用不能靠结束后“清理”代替事前授权。

## 三、评分和指标

### 分层评分

1. 用程序验证可以客观观察的终态与约束，如正确记录是否存在、工具动作是否重复、参数是否合规。
2. 用明确量表评估语义、任务完成和交互质量。接受多种有效解法，不强制与任务无关的工具顺序或文字格式。
3. 用人工确认的正反例、争议例校准裁判。比较新旧文本时可匿名并调整顺序；不要把执行者的解释作为评分依据。

裁判输出应能关联证据，并支持通过、失败、证据不足。量表或裁判变更作为评测系统变更独立记录，重新评分基线；不要与产品改动混成无法解释的一次实验。

### 区分任务结果与执行状态

执行状态记录完成、超时、运行错误、取消和评分缺失；完成后另记任务通过、失败或证据不足。是否把超时和错误计入业务失败率，取决于事先约定的口径，报告不能静默排除它们。

报告总计划数、实际执行数、有效评分数及各类缺失原因。重试必须保留初次结果和后续结果，不能只留下最终成功的一次。

### 可靠性与收益

- 单次成功率：用户一次尝试成功的频率。
- pass@k：在 k 次尝试中至少成功一次的概率，适合允许挑选成功候选的任务。
- pass^k：k 次尝试全部成功的概率，适合检查持续稳定性。
- 配对差异：原来失败而候选成功、原来成功而候选失败、保持不变、无法判断的案例及其重复运行结果。
- 成本与延迟：包含失败、重试、工具调用和裁判的实际消耗；区分最终产品运行成本与本次优化成本。

选择符合产品要求的指标，不必同时报告全部指标。依独立性、样本量和波动采用合适的不确定性估计；不能把存在共同故障的重复运行当成独立证据。小样本分数上涨只支持其测量精度内的结论。

## 四、有边界的连续实验

外层控制器适合管理固定的状态和接受条件，Agent 适合诊断与实现。复用已有运行器；只有用户要求实现时才新增。角色独立不要求不同模型或多个并发 Agent。

### 每轮记录

```text
实验标识及起始版本：
目标失败类别和原因假设：
预期改善、可能退化及证伪方法：
本轮修改及候选版本：
数据、环境、配置与评分版本：
运行证据和执行状态：
新修复、新退化、仍不确定：
成本和剩余预算：
接受、拒绝或证据不足；依据：
当前最佳版本与下一步：
```

### 接受与停止

- 满足合同的改善和约束：接受为新的最佳版本，并保留原始基线。
- 确认退化越过接受边界：拒绝候选；保留产物供诊断，不破坏用户工作区。
- 差异可能来自噪声：在预算内补充有针对性的测量，或报告证据不足。
- 原因假设被否定：重新定位原因，不在同一路线上堆补丁。
- 收益停滞、失败类别来回转移或修改范围持续扩大：检查数据、裁判、需求及方案是否有问题，再决定换路线或结束本轮工作。
- 达到预算或约定停止点：交付当前最佳结果与未完成项，禁止把到限写成完成。

对于无人值守运行，接受条件、预算、协议版本和原始结果应由控制器管理；执行 Agent 不应能直接改写已接受的证据。需要限制访问的文件由权限或运行器隔离，提示词不能提供这种保证。

保存任务状态和原始证据索引，支持中断恢复。重新开始时检查工作区、配置与最佳版本是否一致。增加独立裁判、重置上下文或其他机制后，用同一组代表性任务比较质量、退化、运行成本和可恢复性，再判断该机制是否有价值。

## 方法来源与适用范围

整理日期：2026-10-28。以下来源提供方法依据，不证明某套配置对所有模型和任务最优。使用其具体模型、API 或工具能力时，应另查当前官方文档；普通评测无需每次重新研究来源。

- [Anthropic：Harness design for long-running application development，2026-03-24](https://www.anthropic.com/research/harness-design-long-running-apps)：针对观察到的失败增加机制，再通过逐项简化检查作用。实验主要涉及 Claude 应用开发，不是所有 Agent 的通用对照结果。
- [Anthropic：Demystifying evals for AI agents，2026-01-09](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)：终态评估、裁判校准、环境隔离、能力与回归评测，以及 pass@k 和 pass^k 的区别。
- [OpenAI：Realtime Eval Guide](https://developers.openai.com/cookbook/examples/realtime_eval_guide)：发现、回归与留出数据，以及单轮和完整对话评测。其音频特有方法只适用于相关任务。
- [OpenAI：Optimizing Customer Support Agents for Cost and Quality，2026-09-14](https://developers.openai.com/cookbook/examples/agent_optimization/optimizing_agents_for_cost_and_quality)：固定基线、一次改变一个因素、先检查质量再接受成本收益。示例包含模拟数据，不能将其中数值作为生产效果证据。

- [Percy Liang 等：Holistic Evaluation of Language Models](https://arxiv.org/abs/2211.09110)：明确场景覆盖、同时观察多个指标并统一比较条件，公开测量方法与证据。这里将这些原则用于 Agent 评测；工具副作用、运行预算与授权约束是 AY 的任务适配，不是该论文给出的通用执行流程。
