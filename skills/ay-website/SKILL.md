# AY Website

Design a clear, actionable website.

## Approval contract

<!-- ay-contract:start -->
- Read the full request and investigate discoverable facts before asking the user.
- Treat review, diagnosis, explanation, and planning as read-only unless the user also requests change.
- Treat a precise instruction as approval when target, observable result, and acceptance boundary are clear.
- A broad outcome authorizes investigation, not file or artifact changes based on choices the agent must invent.
- For a materially underspecified change, present one recommended proposal and wait for approval.
- After approval, execute autonomously inside the approved boundary; do not ask about ordinary implementation details.
- Reopen approval only when new evidence changes behavior, architecture, data contracts, dependencies, scope, risk, cost, rollback, or external actions.
- Perform external actions only when the request or approved proposal includes them. Confirm the exact target before an irreversible action.
- Preserve unrelated and user-authored work. Verify the real requested outcome before claiming completion.
<!-- ay-contract:end -->

## Ground the direction

Inspect product facts, audience, visitor action, brand, assets, repository, and supplied references. Inspect reference pages before describing their appearance. Establish what visitors need to understand, believe, and do; give each section a purpose. Never invent testimonials, customer logos, metrics, pricing, or capabilities.

Translate the product's subject and tone into composition, type, color, and imagery choices. Concentrate distinction in one focal idea that explains the product. Recommend one direction when material choices remain open. Extract approved composition and content order as binding layout constraints before implementation. A stacked hero must remain stacked. Delegated creative freedom needs no extra checkpoint.

## Make the direction visible

Design-only work stops at the requested preview or handoff; write frontend code only when authorized. Reuse the existing stack and components; do not assume a framework or animation dependency.

When comparisons are requested, use the requested number of genuinely different compositions and focal images with the same content and viewport. Inspect rendered previews before comparing them. Do not make recolors into separate directions or build several complete sites before a direction is selected.

Prefer real captures and approved media. Label conceptual illustrations and placeholders; never present invented UI as shipped behavior. Keep the hero, lower sections, and action coherent; remove competing elements.

## Verify the visitor's result

Inspect the rendered whole page on desktop and narrow mobile. Check hierarchy, section rhythm, wrapping, overflow, responsive order, semantic markup, keyboard focus, and reduced motion when animation exists. Follow the primary action to its actual destination or observable result; a success toast alone does not prove a working form.

Report source/build, rendered inspection, interaction, and publication evidence separately. If rendering is unavailable, state it and keep recommendations provisional. Never present source checks as visual proof.
